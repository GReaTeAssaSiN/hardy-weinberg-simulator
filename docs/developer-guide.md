# Руководство разработчика симулятора Харди — Вайнберга

Интерфейс на React и TypeScript отправляет параметры расчёта в FastAPI. Сервер проверяет ввод и вызывает функции математического ядра. Интерфейс получает результаты по поколениям и строит графики или таблицы. Формулы и смысл показателей описаны в [руководстве пользователя](user-guide.md#математическая-модель).

## Технические требования

| Задача | Что требуется |
| --- | --- |
| Открыть уже запущенный симулятор | Браузер с включённым JavaScript и доступ к адресу приложения. |
| Получить исходники через Git | Git и доступ к репозиторию. |
| Запустить через Docker | Docker Desktop или Docker Engine с Docker Compose, который поддерживает `docker compose up --wait`. По умолчанию используется порт `8080` компьютера. |
| Запустить локально без Docker | Python 3.12 или новее с `venv` и `pip`, Node.js 24 с `npm`. API занимает порт `8000`. Vite обычно использует `5173` и сообщает фактический адрес в терминале. |

При установке с пустым кэшем нужен доступ к реестрам образов и пакетов. При запуске через Docker Python и Node.js устанавливаются на этапе сборки образов. Для локальной разработки используйте версии из таблицы. [Dockerfile API](../api/Dockerfile), [Dockerfile веб-интерфейса](../web/Dockerfile), [версии среды в CI](../.github/workflows/ci.yml)

Численный минимум по процессору, оперативной памяти и диску для симулятора пока не установлен. Скрипт [замеров производительности](#замеры-производительности) измеряет время ответа при заданной нагрузке.

## Получение исходников

В терминале перейдите в папку, где будет находиться репозиторий, и выполните следующие команды.

```bash
git clone https://github.com/GReaTeAssaSiN/hardy-weinberg-simulator.git
cd hardy-weinberg-simulator
```

Корень проекта — папка с файлами `compose.yaml`, `requirements.txt` и `README.md`. Команды Compose и Python ниже выполняются из неё, если рядом с командой не указана другая папка.

## Структура проекта

| Путь | Назначение |
| --- | --- |
| [`core/`](../core/) | Формирование поколений, миграция, отбор, инбридинг, дрейф, статистика серии и критерий χ². |
| [`api/`](../api/) | Маршруты FastAPI, проверка запросов, ограничения вычислений и формирование файлов CSV и XLSX. |
| [`web/src/`](../web/src/) | Формы, графики, таблицы, сравнение сценариев и выгрузка PNG. |
| [`tests/`](../tests/) | Тесты Python-ядра и API. Тесты интерфейса расположены рядом с компонентами в `web/src/`. |
| [`scripts/benchmark_api.py`](../scripts/benchmark_api.py) | Замеры времени ответа запущенного приложения и проверка ограничения параллельной нагрузки. |

Путь одиночного расчёта начинается в `runSimulation()` в `web/src/App.tsx`. Маршрут `POST /api/simulate` в `api/main.py` принимает JSON и вызывает `simulate()` из `core/simulation.py`. Функция `simulate_rows()` строит строки поколений. Готовый ответ возвращается в React, который отображает его на выбранной вкладке. [Интерфейс](../web/src/App.tsx), [обработчик API](../api/main.py), [цикл поколений](../core/simulation.py)

## Запуск через Docker Compose

Запустите Docker Desktop или Docker Engine с Compose. Из корня репозитория выполните следующие команды.

```bash
docker compose version
docker compose config --quiet
docker compose up --build --wait
docker compose ps
```

`version` показывает версию Compose, а `config --quiet` проверяет конфигурацию. `up --build --wait` собирает образы, запускает контейнеры в фоне и ждёт их готовности. В выводе `docker compose ps` оба сервиса должны быть в состоянии `healthy`. После этого откройте [интерфейс](http://127.0.0.1:8080/), [проверку состояния](http://127.0.0.1:8080/health) или [интерактивную документацию API](http://127.0.0.1:8080/docs).

| Файл | Роль при запуске |
| --- | --- |
| [`compose.yaml`](../compose.yaml) | Определяет сервисы `api` и `web`, их проверки готовности и внешний порт. Сервис `web` запускается после прохождения проверки API. |
| [`api/Dockerfile`](../api/Dockerfile) | Устанавливает зависимости из `requirements.txt`, копирует `core/` и `api/` в образ с Python 3.12 и запускает Uvicorn на порту `8000` внутри контейнера. |
| [`web/Dockerfile`](../web/Dockerfile) | Устанавливает зависимости и собирает React с помощью Node.js 24. Копирует собранные файлы в итоговый образ nginx. |
| [`web/nginx.conf`](../web/nginx.conf) | Отдаёт собранный интерфейс. Запросы к `/api/`, `/health` и документации FastAPI передаёт по внутреннему адресу `http://api:8000`. |

По умолчанию порт `8080` компьютера привязан к адресу `127.0.0.1` и направлен на порт `80` контейнера `web`. `WEB_PORT` задаёт порт компьютера. `WEB_BIND_ADDRESS` задаёт интерфейс, на котором приложение доступно. Для показа в локальной сети подставьте IP компьютера. Ниже пример для macOS или Linux.

```bash
WEB_BIND_ADDRESS=192.168.1.42 WEB_PORT=8081 docker compose up --build --wait
```

В Windows PowerShell те же переменные задаются перед запуском.

```powershell
$env:WEB_BIND_ADDRESS = "192.168.1.42"
$env:WEB_PORT = "8081"
docker compose up --build --wait
```

В этом примере другие устройства в сети открывают `http://192.168.1.42:8081/`. В PowerShell эти переменные действуют в текущем сеансе терминала.

Для смены порта при доступе с самого компьютера задайте только `WEB_PORT`. Например, в macOS или Linux выполните `WEB_PORT=8081 docker compose up --wait` и откройте [http://127.0.0.1:8081/](http://127.0.0.1:8081/). После правок исходного кода повторите запуск с `--build`, чтобы Compose применил новую сборку.

| Команда | Действие |
| --- | --- |
| `docker compose up -d` | Запускает проект в фоне с текущими настройками. |
| `docker compose up --build` | Пересобирает образы и показывает логи в текущем терминале. `Ctrl+C` останавливает контейнеры. |
| `docker compose ps -a` | Показывает работающие и остановленные контейнеры проекта. |
| `docker compose logs --tail=50 api web` | Показывает последние 50 строк для каждого сервиса. |
| `docker compose logs -f api web` | Показывает логи обоих сервисов и продолжает выводить новые строки. |
| `docker compose stop` | Останавливает контейнеры проекта. |
| `docker compose start` | Снова запускает существующие остановленные контейнеры. |
| `docker compose down` | Останавливает и удаляет контейнеры и сеть проекта. Собранные образы доступны при следующем запуске. |

## Локальная разработка

### Установка зависимостей

Убедитесь, что установлена подходящая версия Python. Для проверки выполните `python3 --version` в macOS или Linux либо `py -3 --version` в Windows. Команды `node --version` и `npm --version` должны работать в каждом терминале, где вы запускаете интерфейс или его тесты.

Если в macOS вы устанавливаете Node.js 24 через уже настроенный Homebrew, выполните `brew install node@24`, затем добавьте эту версию в путь поиска команд текущего терминала.

```bash
export PATH="$(brew --prefix node@24)/bin:$PATH"
```

В macOS и Linux создайте окружение и установите зависимости Python.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --cache-dir .cache/pip -r requirements.txt
```

В Windows PowerShell выполните следующие команды.

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --cache-dir .cache/pip -r requirements.txt
```

На любой платформе установите зависимости интерфейса по файлу `web/package-lock.json`.

```bash
cd web
npm ci --cache ../.cache/npm
cd ..
```

### Запуск серверов разработки

В первом терминале запустите сервер с перезагрузкой при изменении Python-кода. Команда для macOS и Linux выглядит так.

```bash
.venv/bin/python -m uvicorn api.main:app --reload --host 127.0.0.1 --port 8000
```

Для Windows PowerShell используйте следующий путь к интерпретатору.

```powershell
.\.venv\Scripts\python.exe -m uvicorn api.main:app --reload --host 127.0.0.1 --port 8000
```

Во втором терминале из корня репозитория запустите Vite.

```bash
cd web
npm run dev
```

Откройте адрес из строки `Local`, обычно [http://127.0.0.1:5173/](http://127.0.0.1:5173/). Vite подхватывает изменения React и передаёт запросы `/api` и `/health` на порт `8000`. Остановите процессы через **Ctrl+C** в каждом терминале. [Настройка Vite](../web/vite.config.ts)

## Маршруты API

| Запрос | Результат |
| --- | --- |
| `GET /health` | Проверка готовности приложения. |
| `POST /api/simulate` | Параметры, строки поколений и сводка одиночного расчёта. |
| `POST /api/simulate/batch` | Средние, процентили, примеры траекторий и статистика фиксации или потери. |
| `POST /api/check-sample` | Частоты аллелей, ожидаемые численности, статистика χ² и вывод по выборке. |
| `POST /api/export` | Готовый CSV. Для Excel передайте `?format=xlsx`. Тело запроса содержит `params` и `rows` из расчёта. |

При локальной разработке интерактивная документация API доступна на [порту 8000](http://127.0.0.1:8000/docs), при стандартном запуске через Docker — на [порту 8080](http://127.0.0.1:8080/docs).

## Проверка запущенного приложения

Для Docker с адресом по умолчанию проверьте состояние и отправьте короткий запрос к API.

```bash
curl -fsS http://127.0.0.1:8080/health
curl -fsS http://127.0.0.1:8080/api/simulate \
  -H 'Content-Type: application/json' \
  -d '{"n": 500, "p0": 0.3, "generations": 2}'
```

Первый ответ — `{"status":"ok"}`. Второй содержит строки для поколений 0, 1 и 2. Во всех трёх строках `p` равна `0.3`. Для проверки через Uvicorn используйте порт `8000`, для Docker с заданным портом — значение `WEB_PORT`.

Чтобы проверить связь интерфейса с API, откройте **«Примеры»** и запустите **«Идеальная популяция»**. Должны отобразиться горизонтальные линии частот `p = 0,3` и `q = 0,7`. Если контейнеры запущены, но интерфейс не показывает результат, посмотрите их состояние командой `docker compose ps -a` и логи командой `docker compose logs --tail=50 api web`.

## Тесты и сборка

Запустите тесты Python из корня репозитория.

```bash
.venv/bin/python -m pytest -q
```

В Windows PowerShell используйте `.\.venv\Scripts\python.exe -m pytest -q`. Чтобы проверить только один файл, добавьте его путь после `-m pytest`, например `tests/test_ideal.py`.

Из корня репозитория перейдите в `web` и выполните тесты интерфейса и сборку.

```bash
cd web
npm run test
npm run build
cd ..
```

Тесты ядра вызывают расчётные функции. Тесты FastAPI отправляют запросы через `TestClient`. Vitest отрисовывает компоненты в `jsdom` и подставляет ответы API. Команда сборки проверяет типы TypeScript и формирует файлы в `web/dist/`.

GitHub Actions запускает проверки при push в `main`, при pull request в `main` и вручную. Для ядра установлен порог покрытия 80%. Для интерфейса проверяются тесты и сборка. [Конфигурация CI](../.github/workflows/ci.yml)

Чтобы локально повторить проверку покрытия из CI, выполните в корне репозитория следующие команды.

```bash
.venv/bin/python -m pip install --cache-dir .cache/pip coverage==7.10.7
.venv/bin/python -m coverage run --source=core -m pytest -q
.venv/bin/python -m coverage report --show-missing --fail-under=80
```

В Windows PowerShell для этих команд используется `.\.venv\Scripts\python.exe`. Результаты измерения сохраняются в служебном файле `.coverage`.

## Замеры производительности

Запустите приложение, затем выполните скрипт из корня репозитория.

```bash
python3 scripts/benchmark_api.py --url http://127.0.0.1:8080 --repetitions 5
```

В Windows PowerShell используйте `py -3` вместо `python3`.

Замер длится от отправки HTTP-запроса до чтения всего ответа. Для одиночного расчёта, серии и выгрузок CSV скрипт выводит медиану и максимум после прогрева. Затем он проверяет ответы на четыре одновременных запроса и выполняет повторный запрос после нагрузки. Если приложение открыто на другом адресе или порту, измените `--url`. [Скрипт замеров](../scripts/benchmark_api.py)
